# Reflect Android: desktop feature parity

Approved direction, November 1, 2026: use Vibepollo for Reflect Host and bring the functional capabilities of Nonary's desktop Moonlight client to Reflect Android. Primary targets remain RTX 5090, Galaxy S23 Ultra and Galaxy Tab S9+. This is the development objective, not a claim that parity has already been delivered.

Reference revisions are pinned in `sources.json`: Vibepollo `1ea3f02717b72de49799cbe06295ea82e236ed60`, desktop client `76ee502543a2305afe06205644611975e3636737`, and its common protocol library `3f9c009fe01db573cd29c1f286db5b7fa8a922fc`. The desktop checkout is `repos/desktop-reference`. Keep its native desktop implementation available for comparison.

## Acceptance rule

Every desktop capability receives a tracked Android outcome: implemented and device-verified, implemented but awaiting hardware validation, missing, or blocked by a demonstrated platform/device constraint. A disabled or decorative setting does not count as support. Preserve Android-specific strengths such as touch, on-screen controls, profiles and lifecycle handling. Desktop-only APIs and UI concepts need functional Android equivalents, not literal copies.

`desktop-preferences.json` inventories all 62 Q_PROPERTY entries in `app/settings/streamingpreferences.h`. Entries start as `audit_pending`; this deliberately includes ordinary preferences and diagnostic/status properties, not just headline features. ## Delivery order

Device progress: [SM-S928U validation](DEVICE_VALIDATION.md) now establishes offscreen GPU compute decoding of PC-generated PyroWave fixtures at 1080p and 3120×1440 in 8-bit 4:2:0/4:4:4. The default mobile fragment path fails reference comparison and remains unqualified. Live transport and Surface integration are still missing.

Foundation progress (2026-11-01): exportable codec/display/native Vulkan diagnostics and a conservative PyroWave feature assessment are implemented. Host advertisement parsing and the common-C/JNI compatibility audit are recorded in [Android capabilities](ANDROID_CAPABILITIES.md). The pinned PyroWave codec and native validation program compile for Android ARM64. Samsung runtime tests, core migration, framing and presentation are still pending; no PyroWave client capability is advertised.

1. **Foundation:** adopt and build the host baseline; retain the tested Android decoder repair; audit capability/ABI differences; collect Samsung codec/display/Vulkan/input diagnostics. Establish HEVC/AV1 interoperability and trace identities.
2. **Shared transport and PyroWave spike:** compile the pinned codec for ARM64, decode recorded frames offscreen, compare golden output, measure GPU time and memory. Then integrate framing/FEC, live presentation, calibration and safe fallback. Do not start by exposing a codec selector.
3. **Presentation parity:** port source-paced policy and diagnostics, implement Android backend/feedback, calibrate both devices. Fixed-refresh behavior remains a first-class supported path.
4. **Peripheral and desktop parity:** implement missing controller/haptics/speaker paths and Remote Monitor UX; close ordinary-preference gaps. USB/Bluetooth protocol investigations may run independently of video work.
5. **Qualification:** complete each inventory item, run 30-minute thermal/network/lifecycle soaks, measure p50/p95/p99 latency and drops, then prepare a signed release.

## Platform constraints to investigate

Android's frame-rate API is a request to the compositor, not a guarantee that the requested rate will be selected. A 120 Hz display specification does not prove desktop-style variable-refresh control is exposed to apps. See [Android frame-rate guidance](https://developer.android.com/media/optimize/performance/frame-rate).

Android has Vulkan and USB host APIs, but their availability alone does not establish that this codec's shader features or a particular controller's output endpoints work on Samsung firmware. Validate Vulkan features/extensions and USB permissions/endpoints on-device. See [Vulkan](https://developer.android.com/games/develop/vulkan/overview) and [USB host APIs](https://developer.android.com/develop/connectivity/usb/host). Bluetooth output and controller audio routing require their own investigation.

The host's WGC, NVENC, RTSS, frame-generation and virtual-driver integrations remain host responsibilities. Android parity means negotiating, controlling where appropriate, and correctly consuming their results; Windows drivers do not move into the Android APK.
